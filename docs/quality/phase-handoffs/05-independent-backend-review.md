## Important findings

1. **Revalidate eligibility and actor authorization under the trip mutation locks.** `apps/api/src/modules/trips/service.ts:286` uses the middleware account snapshot for administrator authorization, and the locked transaction never rereads actor status/roles. Its STARTED branch at line318 checks only the start window and other active trips. It does not check passenger/driver ACTIVE, current DRIVER role, approved/current driver evidence or approved/unarchived vehicle and current insurance. Consequently an accepted booking can start after evidence expiry before the worker reconciles it, and a request already authenticated before suspension can still mutate after suspension commits. Lifecycle11 explicitly requires pre-start qualification revalidation; BR28 requires immediate invalidation. Discover/lock all affected accounts (including actor/passenger where distinct), reread authorization and qualifications in the transaction, and test actual expired evidence and an in-flight suspension race. Turning off new-booking listing alone must not invalidate an otherwise eligible existing commitment.

2. **Finish suspension transaction integration and the create race.** `apps/api/src/modules/admin/service.ts:291` still carries the earlier provider-only placeholder: suspension revokes sessions and disables listing but does not atomically cancel unstarted bookings/release reservations or flag active trips. Those changes currently depend on a later worker run, contrary to BR23/admin14. In addition, `apps/api/src/modules/bookings/service.ts:460` acquires the requester user lock but never rereads requester ACTIVE/current PASSENGER role before creation; a previously authenticated create waiting behind suspension can therefore commit afterward. Use the canonical full resource/account lock set for suspension plus affected aggregates, and check current requester state after create obtains its locks. `lifecycle.integration.test.ts:491` is sequential suspension-before-request, so it proves middleware denial rather than the required suspension-versus-create race. Add synchronized competing transactions and assert immediate persisted cancellation/releases/incidents before any worker tick.

3. **Detect active overdue incidents without requiring a participant transition.** `apps/api/src/modules/bookings/jobs.ts:413` invokes incident marking only for qualification/account-ineligible active bookings; `flagActiveIncident` at line316 returns when qualification remains valid. An otherwise eligible STARTED/IN_TRANSIT trip which passes its planned end remains incidentFlag=false indefinitely until another manual transition (`trips/service.ts:343`). The physical-use conflict guard works, but BR19/lifecycle11 additionally require an overdue incident and a safe extension attempt with protection retained on conflict. Reconcile active overdue work transactionally, leave it active, preserve holds, attempt safe extension or record the conflict incident, and prove repeated ticks do not duplicate audit or release resources.

4. **Require a rejection reason on the server.** `apps/api/src/modules/bookings/decisions.ts:262` determines REJECT but does not require a reason, and line285 persists null when omitted. The shared/OpenAPI input correctly permits an optional reason generally because acceptance does not need one; the conditional domain requirement must be enforced in the service. Lifecycle11 says rejection records a reason. Return422 for missing/blank/short rejection reason without mutating decision/trip/history/reservations; preserve successful reasoned rejection coverage.

This is an explicit contract limitation, not permission to invent a prior status. Reconcile the nullable creation representation in a future contract/UI hardening pass if complete visible creation history is required.
