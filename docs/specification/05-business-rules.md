# 05 · Business Rules

Status: proposed implementation baseline; implementation requires separate human approval.

## Normative rules

| BR18 Trip start | Driver/admin; ASSIGNED; DB now in [starts_at-15min, starts_at+30min]; all approvals/qualification still valid; no other STARTED/IN_TRANSIT using either resource; parent confirmed/published. Rental requester is actual driver |
| BR19 Overrun | Clock passing ends_at cannot release a resource still in use; active trip guard blocks next start. Flag overdue; attempt reservation extension under constraints; if conflict, keep active resource guarded and alert admin to cancel/reassign upcoming trip. | BR20 Verification | DRAFT->PENDING->APPROVED/REJECTED; APPROVED->EXPIRED by worker or invalidated DRAFT by material edit; new immutable revision on resubmission. Pending/approved docs cannot be removed; material edit with live/future commitments409 until cancelled/resolved |

Hidden reviews excluded SQL aggregate; no mutable client aggregate |
| BR23 Suspension | Immediate JWT/session invalidation via DB check; atomic future cancellations/seat releases, listing eligibility disabled; active trip incident retained for admin response. Lock affected accounts/resources through standard protocol; no restoration on reactivation |
| BR24 Privacy | Private docs/phone/license/registration never public; public DTO differs own DTO; object checks through owning parent; administrator sensitive reads audited; text rendered plain, never HTML |

## Transaction lock protocol
Use READ COMMITTED plus explicit row locks and database constraints; correctness must not depend on an ORM default isolation feature. Determine affected account IDs, driver IDs, vehicle IDs, booking/carpool IDs before locking; acquire user rows ordered UUID, then driver_profiles ordered UUID, then vehicles ordered UUID, then booking/carpool aggregate rows ordered UUID, then child request/decision rows ordered UUID. Read dependencies, lock, re-read and verify unchanged; retry discovery if the set changed. All resource and eligibility mutations (including suspension, archival, blocks and verification) follow this protocol. Seat-only operations lock relevant user rows, then carpool row, then request; never acquire a resource lock later. Suspension pre-discovers all affected aggregates, locks resource set, rechecks before writes; creates cannot race because user/resource locks are shared protocol.

Persist domain writes, histories, admin audit, idempotency result and outbox events in the same DB transaction. No SMTP/file scan/HTTP call inside locks. Use bounded3-attempt jittered retry only for deadlock40P01/serialization40001; preserve key and request hash across retry. Map exclusion23P01 to409 RESOURCE_CONFLICT, unique23505 to context-specific409. If an intermediate failure occurs, roll back all related writes. A bounded retry exhaustion returns503 RETRYABLE_TRANSACTION. A failed business precondition is not retried automatically.

## Cross-row invariants
Resource reservation source is exactly one booking/carpool/block; resource exactly one driver/vehicle. Trip belongs to exactly one booking/carpool. Each live booking/carpool must have exactly two live reservations matching its actual resources. Seat count bounds are DB CHECK; sum equality is maintained by single locked service and reconciliation read. Aggregate states/history agree. Tests assert these across cancellation, expiry, suspension and worker replay. DB triggers/constraints enforce immutable ownership, append-only history and audit where appropriate; repositories cannot bypass domain service authorization.
