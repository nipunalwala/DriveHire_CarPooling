# Principal-engineer planning reviews

## Review 1 — requirements, architecture and operational rules
Inspected all requested capability areas: auth/roles, drivers, vehicles, three hire modes, carpool seats, ride lifecycle, ratings, notifications, complaints, admin, deployment and exclusions. Corrections made while drafting: one shared typed driver/vehicle reservation table for bookings, carpools and maintenance blocks; explicit resource holds even for self-drive and host rides; finite availability windows; independent booking/trip/seat state machines; quote snapshot versus hold distinction; current verification at each mutation; suspension active-trip incident policy; provenance of generated images. No critical functional area left without a requirement/phase. Risk still requiring owner at public launch: operating region/currency/retention and production provider credentials.

Normalized ownership/verification snapshots, unique live requests, immutable histories/audit, typed source/resource XOR and partial GiST exclusions reviewed for the stated race scenarios. Prisma custom SQL migrations and introspection are required. Phase order verified: providers before booking, booking before carpool shared holds, lifecycle before reviews, backend before dashboards, integrated app before security/QA/deploy. No circular code dependency is required: early domain modules emit durable events; later notification handlers consume them. Early qualification expiry affects only qualifications until live commitments exist; booking and carpool phases extend its domain service, not a placeholder.

## Review 2 — fresh coding agent execution
Each phase packet includes A–P structure, explicit task sequence/file responsibility, owned API operation IDs with method/path/role/request/success, entity requirements, UI scope, negative/concurrency scenarios, measurable acceptance, verification commands, branch/commit and handoff. The master guide maps every FR to phase/API/entity/screen/test. A fresh session reads canonical referenced specifications, verifies prior handoff and applies test-first Superpowers workflow. Unresolved deployment input is isolated to Phase23/public launch; no phase needs to invent how a seat is held, a trip advances or provider consent works.

Consistency decisions corrected during review: no registration API-admin grant, no self-approval, no automatic route/GPS, no payment/refund state, driver-only uses requester-owned approved vehicle, rental requester must be approved driver, report is estimated value rather than revenue. Impeccable proposed visual direction is documented, and generated marketing imagery is a future project asset with prompt/provenance. The context launcher could not run in this sandbox; its SKILL.md and historical design evidence were read directly. This is a design specification, not visual implementation evidence.

## Remaining decisions and evidence limits
Plan is a proposed implementation baseline, not current production readiness. Exact supported dependency versions, hosting/SMTP/storage/scanner accounts, legal operating permission, operating region and retention must be resolved at their designated gates. No application tests, migration deployment, UI screenshot, load result or restore test has run because implementation is explicitly excluded. The documentation checker verifies internal structure/traceability and local files; OpenAPI conformance against a live implementation waits Phase20. No new GitHub repo was created per latest user direction; same remote/history used.
